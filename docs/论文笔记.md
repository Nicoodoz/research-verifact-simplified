DOI：10.1056/AIdbp2500418

作者单位：Stanford University School of Medicine、Stanford Health Care

# 一、abstract

## 1. BACKGROUND

**大型语言模型（LLM）能够生成临床文档，但有幻觉**，依次人工矫正不现实。近年来，一个越来越常见的人工智能应用趋势是使用 LLM 来评价其他 LLM 的输出，也就是 **LLM-as-a-Judge，**有研究表明，这种方法与人类判断之间可以达到较高的一致性

## 2. METHODS

作者建立了一个基准数据集 **VeriFact-BHC、以及一个 VeriFact 系统**

## 3. RESULTS

## 4. CONCLUSIONS

VeriFact 可以帮助临床医生在由 LLM 起草的文档被正式写入患者 EHR 之前，对其中的事实进行核验。

它也可以用于自动化那些原本需要人工查阅病历的任务。

同时，VeriFact-BHC 可以作为一个 benchmark，用于开发和评价新的患者临床文档事实核验方法。

# 二、Introduction

## 1. VeriFact做了什么：

VeriFact 通过把 LLM 生成文档中的陈述与患者 EHR 中的事实进行比较，执行**患者特异性的事实核验（patient-specific fact verification）**。

## 2. 相关研究：

已有的一些研究会使用 Google 搜索结果或 Wikipedia 作为参考资料，但这些方法无法针对某个患者独特的病史进行判断。

## 3. 为什么要拆成 proposition 和 fact：

VeriFact 会把**长文本拆分成若干个可以独立核验的陈述**。

这些待核验的陈述称为 **propositions（命题）**，来自BHC（分为 LLM-written BHC、human-written BHC，都有标注数据），也可以理解为需要进行事实核验的假设。

与此相对，从患者历史 EHR 中得到的陈述称为 **facts（事实）**，这些内容被假定为真实。

对于每个 proposition，系统都会从患者 EHR 中检索相关 facts，并据此判断该 proposition 属于：

- `Supported`
- `Not Supported`
- `Not Addressed`

# 三、Methods

## 1. Dataset Creation：数据集是怎么构造的

VeriFact-BHC 基于 **MIMIC-III Clinical Database v1.4** 构建，因为它包含纵向临床笔记，更接近一个真实生产环境中的 EHR。

抽取了 **100 名患者，**

**1️⃣从 出院小结 中抽取真实医生写的 BHC，**

**2️⃣其余临床 notes 合在一起，形成这个患者的 reference EHR。**

**3️⃣用 Llama-3.1-70B-Instruct，基于该患者最近一次住院期间的所有 EHR notes，再生成一份 LLM-generated BHC**

## 2. BHC 怎么变成 propositions

Sentence proposition：一句一个proposition，使用 NLTK sentence parser 生成

Atomic claim proposition ：Llama-3.1-70B-Instruct动态拆分为不可分割的陈述

## 3. Data Annotation：医生到底是怎么标的

每一条 proposition 都被医生标成三类之一：

- `Supported`：EHR 提了，且支持这条proposition
- `Not Supported`：EHR 涉及这件事，但没有完全支持，甚至可能矛盾；
- `Not Addressed`：EHR 根本没提

两种分割方法分别标注

## 4. The VeriFact System：VeriFact系统怎么工作

VeriFact = RAG + LLM-as-a-Judge

**整体流程：待核验 BHC--->提取 propositions--->每个 proposition 单独处理--->从同一患者 EHR 中检索 Top-N证据--->组成 reference context--->大模型判断--->输出标签（Supported / Not Supported / Not Addressed）和理由**

**患者 EHR 提前处理：患者所有 EHR documents--->拆成 sentence facts / atomic claim facts--->生成 embeddings--->放进 vector database**

## 5. 检索器

BAAI/bge-m3 的两种表示dense semantic embedding（稠密，偏语义）和sparse lexical embedding（稀疏，偏词面）

## 6. reference context怎么组织

检索出的各个fact按照时间排序，附带日期、时间、note 类型；

## 7. 输入给大模型以后怎么回答

给出三分类 verdict和判断理由

作者共比较了9个模型，没做任何训练

# 四、Results

## 1. Dataset and Annotation：数据集和标注结果

VeriFact-BHC 最终包含 **100 名患者**。每名患者都有：

- 一份 LLM-generated BHC；
- 一份 human-written BHC；
- 该患者对应的 EHR 临床记录。

最终数据集中共有 **13,070 条 proposition**，其中：

- **4,445 条**来自 LLM-generated BHC；
- **8,625 条**来自 human-written BHC。

按 proposition 类型分：

- **9,095 条 atomic claim propositions**
- **3,975 条 sentence propositions**

每条 proposition 都由至少 3 名临床医生标注。

## 2. Clinician Inter-Rater Agreement：医生彼此之间有多一致

对于 **LLM-generated BHC**：

- Atomic claim proposition：医生一致率 **88.5%，大，说明更容易标，争议小**
- Sentence proposition：**84.7%**

对于 **human-written BHC**：

- Atomic claim proposition：**73.3%**
- Sentence proposition：**66.9%**

## 3. Preliminary Sensitivity Analysis：先选系统配置

先把 retrieval 侧大致选好，rerank retrieval、absolute time reference context、只检索 current admission 效果最好，就用这几个做实验，而不是 每换一个 Judge 模型都重新调 retrieval

## 4. 性能指标

Percent Agreement ：AI 和医生最终标签有多少比例完全一样

Gwet’s AC1 ：扣除部分“偶然一致”后的标注一致性

MCC ：三个类别整体分得好不好，相当于提高了少数类的权重，不再只有多数类主导。这个指标最重要

# Limitations：作者自己承认的局限

1. 作者没有探索更多：retrieval models、reranking models

2. 没有医学专用模型，也没做领域微调

3. 作者使用了一套固定 prompt，没有进一步系统优化 prompt。

4. VeriFact 把 EHR 当作事实来源。但这存在问题：

   第一，如果患者刚进入这个医疗系统，历史 EHR 很少，即使某个事实医生和患者都知道，系统也可能因为找不到记录而判断成 Not Addressed。

   第二，EHR 本身也可能包含错误，例如：

   - 误诊；
   - 沟通错误；
   - 复制粘贴造成的过时信息。

   因此，VeriFact 的准确性受制于 EHR 本身的数据质量。

5. 不能检查：**应该写但没写的内容。**

6. human-written BHC 性能明显下降，未来需要研究：如何构建一个在人工撰写的临床文档上也同样表现良好的评价系统。
