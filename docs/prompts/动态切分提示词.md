## 1. 项目背景与策略演变

### 1.1 当前项目要解决什么问题

本仓库研究临床自由文本与原始 EHR 证据的一致性。Hospital-02 这条研究线以医院检查、检验、微生物、药敏、病理和诊断记录为证据，核验病程记录里引用的数值、定性结果、日期等客观事实是否与原始报告一致。`EHRCon`、`Hospital-01-OR` 及 `MIMIC` 相关资料不属于本文实验的数据来源。

Hospital-02 的上游流程是：

```text
Stage 01 脱敏 XLSX
  → Stage 02 解析 XML，标准化 Report / Section / Evidence
  → Stage 03 整理报告级事实底稿
  → Stage 03B 冻结 500 报告队列，按患者隔离 dev / valid / test
  → Stage 04 规划受控事实变异
  → Stage 05 生成 consistent / inconsistent 临床文本
  → Stage 06 核验最终生成文本，形成事实标注
  → Stage 06B 聚合批次
  → Stage 07 冻结 corpus / documents / document_units / qrels
```

因此，动态切分面对的是**基于真实脱敏报告生成的临床自由文本**，其中有正确版本，也有人工设计变异后生成的不一致版本。它不是直接切分原始 XLSX，也不是在一批未经生成的真实病程记录上做完整临床验证。

### 1.2 为什么从整篇/段落检索改为事实检索

一篇文本往往同时包含多个检验项目、日期、诊断和治疗建议。整篇文本只检索一次时，所有事实共享同一组 Top-k；高频词或某个较长项目可能主导排名，其他项目的证据落到 Top-k 之外。段落切分虽缩短了 query，但一段内仍可能有十余个项目，不能保证“一项事实对应一次检索”。

动态事实切分用模型识别关系边界，把“项目—结果”或“药物—药敏结论”拆开，并保留能从原文定位的上下文。切分数量随正文事实数量变化，单篇上限为 40 条。

| 版本/模式 | 切分与检索方式 | 提示词/输出特点 | 对应状态 |
|---|---|---|---|
| `query_mode=document` | 整篇正文一次检索，各事实共享排名 | 不需要切分提示词 | `exp500_v1/final_v7` 正式基线；也是公平评价中的 Document 对照 |
| `query_mode=unit` | 按空行、编号项切分；长于 260 字符时尽量按句子重新组合，附标题及相邻句上下文 | 本地规则，无 LLM 提示词；不是严格字符窗口，超长单句可能仍超过 260 字符 | Stage 07 共 1,265 个结构单元 |
| `factplan.v1` | LLM 抽取最小关系，最多 12 条 | `document_quote + claim_type + anchors`；含影像/病理所见、诊断等较宽类型 | 2026-07-17，964 文档、4,276 单元；历史产物 |
| `factplan.v2` | LLM 抽取任务相关关系，每单元独立 Top-k | `document_quote + context_quotes + fields`；最多 40 条，显式截断标记 | 964 文档、4,351 单元；本文主体 |

旧目录中的 `document_global5` 曾把多个事实的候选合并为全文共享 5 张证据。当前 `llm_fact` 入口已禁止该模式；v2 正式运行使用 `unit_topk`、每单元 Top-10，再离线报告 @1、@3、@5、@10。

注意两个不同的“v1”：`exp500_v1` 是原冻结实验的名称，`factplan.v1` 是第一版 LLM Planner。本文结果表中的 Document 基线来自前者；它不是旧 LLM Planner。

## 3. 动态切分怎么接入流程

```text
Stage 07 documents.jsonl
  │ 只取 body_text；必要时由 document_text 去除固定文书头
  ▼
Stage 08A：system prompt + 12 对 few-shot + 当前正文
  → Flash 返回结构化 JSON
  → 本地检查原文定位、字段来源、必填字段、去重、截断
  → 满足修复条件时调用 Pro
  → 仍无可用结果/异常时写入回退单元
  ▼
planned_units.jsonl
  │ 每条含 unit_text、local_context、fields、retrieval_query
  ▼
Stage 08：query_mode=llm_fact，budget_mode=unit_topk，top_k=10
  → 由业务/benchmark 上下文确定患者范围
  → BM25 / BGE-M3 Dense / RRF60 独立排序每个事实的证据
  ▼
retrieval_results.jsonl
  ▼
stage-10-factplan：此时才读取 qrels 和 Stage 06 标注
  → 事实与动态单元 linkage → 相同分母指标 → bootstrap → coverage gate
  ▼
动态 Stage 09：当前未启动
```

**Planner 负责忠实抽取正文声称的内容，不判断真假，也不纠错。** 如果正文写了错误数值，Planner 仍应保留该数值，后续才用原始 Evidence 核验。把 Gold 数值喂给 Planner 会破坏实验的独立性。

API `messages` 只包含系统指令、示例正文/示例答案和当前正文，不传患者检索范围、Evidence Card、Evidence ID、qrels、变异计划或一致性标签。`planning_requests.jsonl` 外层的 `input_id`、`request_id`、`split` 是本地追踪字段，不属于发送的 `messages`。`local_document_context` 是上游生成文书头使用的信息，与这里的 `context_quotes` 不同。

这条边界建立在已经脱敏的 Stage 07 正文上；`_strip_header()` 只移除固定格式的“【病程记录】/时间”头部，并不是通用脱敏器。

## 4. v2 实际使用的提示词

### 4.1 System prompt 全文

来源：`stage_08a_plan_queries.py`（旧项目路径：`../../src/Hospital02LabReports/pipelines/stage_08a_plan_queries.py`） 的 `SYSTEM_PROMPT`。已逐条核对正式运行的 964 个请求：其 system 内容均与下文一致。

```text
你是 Hospital-02 的医学事实检索单元规划器。只依据输入正文抽取当前任务可核验的事实：
1) 定量检验值；2) 定性检验值；3) 报告日期；4) 微生物培养菌种/菌量；5) 每一种药物的药敏结论。

一个单元只表达一个关系，但必须保留该关系检索所需的上下文。document_quote 是待核验关系的连续原文；context_quotes 是正文中连续原文，用来提供项目名称、检查名称、菌种、标本或日期。

规则：
- 每个检验项目一条；不要只抽异常值。
- 每个药物的敏感、耐药、中介或非敏感结论一条；多个药物共享一句原文时仍必须逐药物输出。
- 实验室报告日期附在具体检验项目 fields.report_date；微生物日期附在菌种或药敏单元；检查报告日期必须与检查名称组成 examination_report_date 单元。
- 不要抽诊断、病理、影像所见、治疗建议、推测、风险提示、沟通内容或“其余项目正常”等无法指向具体项目的概括。
- 所有字段值必须原样出现在 document_quote 或 context_quotes 中；不得补充外部知识，不得改写数字、日期、单位、药名或结果。fields 只输出有值的键，禁止输出空字符串或 null。
- document_quote 必须在正文中唯一定位；若短语重复，请扩展 quote 到能唯一定位。
- 最多 40 条。若仍有遗漏，设置 truncated=true 并报告 omitted_count；绝不能静默截断。

只返回 JSON：
{"document_type":"laboratory|examination|microbiology_susceptibility|mixed|other","units":[{"document_quote":"","context_quotes":[""],"claim_type":"laboratory_quantitative|laboratory_qualitative|examination_report_date|microbiology_organism|susceptibility","fields":{"item_name":"","value":"","unit":"","reference_range":"","panel_name":"","report_date":"","exam_name":"","exam_date":"","organism":"","organism_quantity":"","drug":"","result":"","result_code":"","mic":"","test_method":""}}],"truncated":false,"omitted_count":0}
```

末尾 JSON 中的空字符串是在提示输出结构；执行规则仍要求只输出有值的字段。当前代码的 `_complete()` 最低要求为：定量/定性检验有 `item_name + value`，检查日期有 `exam_name + report_date`，菌种有 `organism`，药敏有 `drug + result`。程序不会强制每条检验都包含单位或日期。

早期改进方案将目标概括为“四类事实”，当前正式 prompt/schema 明确列出 **五种 `claim_type`**，其中单独保留了 `microbiology_organism`。

### 4.2 User prompt 与完整 messages 结构

当前文档的 user 消息就是一个 JSON 字符串：

```json
{"document_body": "去除固定文书头后的临床正文"}
```

正式请求共 26 条消息，按如下顺序发送：

```text
1 条 system
12 ×（user: {document_body: 示例正文}
      assistant: {document_type: "example", units: 示例单元,
                  truncated: false, omitted_count: 0}）
1 条 user: {document_body: 当前正文}
```

少样本内容是完整提示词的一部分；只复制 system 文本属于 zero-shot，不等价于当时的正式实验。完整 12 条示例在 `stage08a_factplan_v2_fewshot.jsonl`（旧项目路径：`../../configs/Hospital-02-LabReports/stage08a_factplan_v2_fewshot.jsonl`），正式请求快照在 `planning_requests.jsonl`（旧项目路径：`../../outputs/Hospital-02-LabReports/experiments/exp500_v2_factplan/v2_stage08a_all/planning_requests.jsonl`） 的 `api_request.messages`。

| 3 | 肝肾功能/电解质等 | 214 | 2 | 定量 2 |

提示词指纹：

```text
prompt_sha256 = 318038d11c90d13992bfff3c7a749c19e28a30dfe5655072509f87b98e8bdf14

```

`prompt_sha256` 按 `SHA256(SYSTEM_PROMPT + json.dumps(examples, ensure_ascii=False, sort_keys=True))` 计算。两个指纹已与冻结文件和四个 shard manifest 核对。

### 4.3 Pro 修复提示词

修复仍使用同一 system prompt，但不重复附带 12 条 few-shot，也不把上一轮答案整段传回去。user 消息如下，`audit` 由本地程序填写：

```json
{
  "document_body": "当前完整正文",
  "repair_instruction": "重新完整抽取；修复以下本地审计发现的疑似遗漏或截断。只返回最终完整 JSON。",
  "audit": {
    "valid_units": 0,
    "rejected_units": 1,
    "truncated": false,
    "repair_needed": true
  }
}
```

上面的 `audit` 数字是格式示意，不是某个真实调用记录。当前代码只在**已经取得可解析的 units 数组，且截断/声明遗漏或验证后没有有效单元**时进入 Pro 分支；部分单元被拒绝、仍有有效单元时，不会自动触发修复。HTTP/JSON 解析等异常在重试耗尽后会进入回退，并非所有格式错误都会交给 Pro。

### 4.4 实际模型和调用参数

| 参数 | 当前实现与冻结运行 |
|---|---|
| 主模型 | 冻结响应为 `deepseek-v4-flash`；程序从 `DEEPSEEK_MODEL` 读取，默认亦为该模型 |
| 条件修复模型 | `--repair-model deepseek-v4-pro` |
| temperature | Stage 08A 强制 `0` |
| thinking | `disabled` |
| response_format | `{"type":"json_object"}` |
| stream | `false` |
| max_tokens | `min(DEEPSEEK_MAX_TOKENS, 8192)`；环境值默认 32768，因此通常实际封顶 8192 |
| 最大尝试次数 | CLI 默认 `--max-attempts 2`；主调用和条件修复各自按该上限重试 |
| Pro 超时 | `min(DEEPSEEK_TIMEOUT_SECONDS, 60)` 秒 |

这些是本地代码及历史响应记录，不代表对当前外部服务可用性或价格的验证。

## 5. 输入、输出和检索 query

### 5.1 三个层次的输入输出

| 层次 | 输入 | 输出 |
|---|---|---|
| 模型抽取 | `document_body` 与提示词 | `document_type`、`units[]`、`truncated`、`omitted_count` |
| Stage 08A 本地记录 | 模型 JSON、原正文及本地追踪 ID | 每个事实一行的 `planned_units.jsonl` |
| Stage 08 检索 | planned units、corpus、患者范围 | 每个事实一行 `retrieval_results.jsonl`，内含 Top-k 证据数组 |

Stage 08A 记录中的 `input_id` 对应 Stage 07 的 `request_id`；Stage 08A 自己的 `request_id` 是 `factplan_v2_...` 调用标识。`planned_unit_id` 在 Stage 08 输出中写作 `unit_id`。

### 5.2 模型单元如何变成本地单元

| 字段 | 含义及生成方式 |
|---|---|
| `document_quote` → `unit_text` | 被核验的连续原文；必须在正文中恰好出现一次 |
| `context_quotes` | 正文中存在的上下文连续片段；上下文片段本身不要求唯一 |
| `local_context` | `context_quotes` 按换行连接，不固定等于 `unit_text` |
| `claim_type` / `fields` | 事实类型与有原文依据的字段；非空字段值必须出现在 quote 或 context 中 |
| `retrieval_query` | 本地 `_query()` 按固定中文字段模板生成，非模型自由改写 |
| `planned_unit_id` | 由文档 input ID、claim_type、quote、排序后的非空 fields 生成稳定哈希 ID |
| `fallback_used` | 是否由失败回退生成 |
| `preview_only` | 是否仅为 dry-run 预览产物 |

去重键是 `(claim_type, quote, fields)`；多个药物可以共享同一整句 quote，只要药物字段不同，就生成不同单元。当前稳定 ID 不包含 context，因此只修改上下文、未修改字段时，ID 未必变化。

### 5.3 各类 query 模板

所有 query 以 `原文事实: {quote}` 开头，再按下表追加有值的字段，各段用 `；` 连接。字段名称直接对齐 Evidence Card 的中文字段。

| claim_type | 报告类型 | 追加字段 |
|---|---|---|
| `laboratory_quantitative` | 检验子项结果 | 检验子项名称、检验子项结果（定量）、检验子项结果单位、检验子项参考值范围 |
| `laboratory_qualitative` | 检验子项结果 | 检验子项名称、检验子项结果（定性，阴/阳）、检验子项参考值范围 |
| `examination_report_date` | 检查记录 | 检查项目描述、检查日期、报告日期 |
| `microbiology_organism` | 微生物培养生成细菌信息 | 细菌名称、细菌计数 |
| `susceptibility` | 细菌的药敏信息 | 抗生素名称、最低抑菌浓度、药敏结果代码、药敏结果描述、试验方法 |

当前 `_query()` **并未将所有 fields/context 自动拼入检索词**：例如检验的 `panel_name/report_date`、药敏的 `organism/report_date` 不在对应模板中。Stage 08 有 `retrieval_query` 时直接使用该字符串，不再自动追加 `local_context`。因此“模型保留了日期/菌种上下文”和“实际检索利用了这些上下文”是两个不同条件。

## 8. 实验效果

### 8.1 评价口径

正式结果来自 `stage08_fair_eval_v2`（旧项目路径：`../../outputs/Hospital-02-LabReports/experiments/exp500_v2_factplan/stage08_fair_eval_v2`），不使用旧 `stage08_fair_eval_v1` 的单方法历史总览。

评价先将 Stage 07 qrels 展开为事实，用 Stage 06 标注与同文档 planned units 建立 linkage，再读取已经生成的排名。事实必须能唯一链接才算 `linked`；没有对应单元为 `uncovered`，有多个无法消歧的候选为 `ambiguous`。这是一项受抽取和链接规则共同影响的 **Planner/linkage coverage**，不是逐条人工判定的抽取准确率。

共同分母保留全部 2,350 条事实。未覆盖、歧义和缺少动态排名都按 miss 处理，不从分母删除。每条事实恰好有 1 张 Gold Evidence Card，因此本实验的 Any-hit@k 与 Mean Evidence Recall@k 数值相同。

本文主表使用 `dynamic_fact_unit_topk_unconditional`。`conditional` 只在 1,999 条成功链接事实上计算，用于判断后端检索是否仍有提升空间。两者关系在本次数据上为：

```text
总体 Recall@5 = Planner coverage × linked 事实上的 conditional Recall@5
BM25：0.8506 × 0.9515 ≈ 0.8094
```

Bootstrap 按 `patient_group_id` 聚类成对重采样 10,000 次，基础随机种子 `20260717`；代码按 `[all, dev, test, valid]` 的顺序为各分组使用 seed + index。相同患者组同时进入基线与动态方案的差值计算。valid 是方案指定的主要比较集；test 按改进方案视为 post-hoc exploratory，不能重新包装成完全未参与开发的前瞻验证。

| dev | 486 | 416 | 66 | 4 | 0.8560 | 72 |
| valid | 508 | 446 | 53 | 9 | 0.8780 | 73 |
| test | 1356 | 1137 | 189 | 30 | 0.8385 | 221 |

所有检索器共用同一个 Planner/linkage。三套正式评价的 `dynamic_missing_rankings_for_linked_facts` 和 `baseline_missing_rankings` 均为 0，因此表中的主要损失来自未覆盖和歧义，而不是排名文件缺失。

## 9. 早期方案与当前实现的差异

阅读 `LLM动态切分v2改进方案.md`（旧项目路径：`LLM动态切分v2改进方案.md`） 时应注意，它描述的是设计目标。本文按实际源码补充以下边界：

| 设计意图/容易产生的理解 | 当前真实行为 |
|---|---|
| 本地关系覆盖审计发现漏项后交给 Pro | 验证器检查 quote、fields、必填项及显式截断；没有遍历全文全部候选关系的完整覆盖审计。部分漏项可能不触发修复 |
| 修复后仍不完整就统一规则补齐 | 有有效单元且仍声明截断时，可保留结果并记录 `repair_incomplete`；异常或没有有效单元才回退 |
| 回退能按任务类型抽取有效事实 | `_fallback_units()` 实际调用段落/句子切分，再写 `examination_report_date` 与“未知检查/未知”占位字段；它不是五类事实专用规则抽取器 |
| 保留 context 就保证检索利用全部上下文 | 对应 query 模板并未使用所有 fields；有显式 query 时 Stage 08 不追加 `local_context` |
| prompt schema 被严格验证 | 当前不校验 `document_type` 枚举，也不进行完整 JSON Schema 校验；部分空值在落盘前被清除 |
| `--resume` 会复用完成的模型结果 | 当前 Stage 08A 没有实现读取已有响应、跳过已完成请求的执行缓存 |
| `stage-08/metrics.json` 就是动态正式分数 | 动态 ID 与原 qrels 的结构 unit ID 不同，默认评价会返回 `evaluated_queries=0`；必须使用 `stage-10-factplan` 的 linkage 和同分母评价 |

尤其不要将以下实际文件解读为“动态召回率为零”：

```json
{
  "evaluated_queries": 0,
  "reason": "no_qrels_matched_runtime_units"
}
```

这是 `v2_stage08_bm25/metrics.json` 的实际内容，表示旧评价函数无法直接匹配新单元 ID，不是一个有效的召回率结果。正式数值应读取 `stage08_fair_eval_v2/bm25/metrics.json`。

后续改进方向包括：修复检查日期抽取/链接，补全 few-shot 的逐项答案，增加正文候选关系覆盖审计，将经过验证的日期/菌种等上下文纳入对应 query，并将回退事实与正常模型事实分开审计。它们是由当前结果和代码推导的待验证方向，不是已经证明有效的新实验结论。

## 10. 历史 v1 提示词与定位入口

### 10.1 `factplan.v1` 原始 system prompt

以下直接取自 `stage08a_all_v1/planning_requests.jsonl`，用于说明从宽类型、12 单元上限向任务相关 v2 演变的背景。不要用它复现本文 v2 数值。

```text
你是医学文书事实查询规划器。只根据给出的正文抽取最小、可独立核验的关系单元。
单项检验一项一单元；每个药敏药物结论一项一单元并保留菌种/标本/日期上下文；影像或病理的明确所见一项一单元。

claim_type 只能是 laboratory_quantitative, laboratory_qualitative, microbiology, susceptibility, examination_finding, pathology_finding, diagnosis, date_or_report_context。
只返回 JSON：{"units":[{"document_quote":"...","claim_type":"...","anchors":{"organism":"","drug":"","result":"","date":""}}]}。最多 12 个单元。
```

v1 的示例文件为 `stage08a_factplan_fewshot_v1.jsonl`（旧项目路径：`../../configs/Hospital-02-LabReports/stage08a_factplan_fewshot_v1.jsonl`）。v1 全量产物有 4,276 单元、28 个回退文档；其 `unit_top5` / `document_global5` 结果与 v2 的 schema、query 及评价口径不同，不构成本文的同口径 v1-LLM 对照。
