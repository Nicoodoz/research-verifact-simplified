# 009：检索基线比较与证据损失定位

**建议后续暂用 C48：原claim → BM25与BGE-M3两路交替保留48候选 → 原claim重排 → Judge，同时保留A48作为对照。纯dense B48没有显示整体优势，尤其损失了human组的Supported召回。C48是成本与复杂度相近的实用选择，还不是已证明稳定优越的新方法。下一步优先验证证据组织是否能保住检查身份、事件时间与实施状态，再区分Judge支持边界；暂不扩大通用planner或继续搜索融合参数。**

实际出现了局部证据改善，但总体优化有限：C相对A，LLM净正确数不变，human净增3条；无法据此确立论文主线。009已完成真实实验、诊断与执行自查，等待独立复核。原数据、001–008历史成果和全部既有回答保持不变。

## 实际比较了什么

先在008已使用的6名患者、144条命题上开发；确认前冻结方案，再使用原开发哈希顺序第19–24名患者 **59250、93640、15057、27036、59840、66218的全部650条valid atomic claims**。LLM-written 243条（S/NS/NA=228/10/5），human-written 407条（313/27/67）。保留16名后续开发患者及40名reserved test，不根据结果重抽样。

新确认从本地原始EHR构建 **413份note、2,498个原文片段**：按目标住院日历日CHARTDATE筛选、排除出院小结；3份超出日期范围的note排除。逐段位置、note哈希与所有非空白字符覆盖均核查，没有把发布reference当新检索语料。

|条件|送入共同重排器前的候选规则|其他环节|
|---|---|---|
|A48：当前基线|BM25与dense各取前80，RRF(k=60)融合后取48|三臂相同|
|B48：语义基线|原claim的dense前48|三臂相同|

索引、词面BM25、cosine排名与融合在本地完成；硅基流动API计算BGE-M3 dense、BGE reranker及DeepSeek-V4-Flash。每条claim三臂候选并集一次真实重排，各臂只使用本臂候选。**BM25不是BGE-M3 learned sparse**。这是可复现的本地baseline，不是原VeriFact系统的逐字等价复现。[官方BGE说明](https://huggingface.co/BAAI/bge-m3)、[作者固定版本实现](https://github.com/philipchung/verifact/blob/f115d36cb65fa2073fce0a10df56bb37f4cbcd50/packages/llm_judge/src/llm_judge/reference_context.py)及差异见[核对底稿](../../tasks/009_retrieval_baselines/research_notes.md)。

最终都用**原claim、原structured提示、同一Judge设置**（temperature=0、thinking=false、max_tokens=2048）；来源上下文不进入Judge。每臂最多16完整段、每note最多2段，正文连记录头最多8,000字符，住院总头另计；不截掉入选段尾部，不按最短臂清空其他臂。三臂平均完整输入约3,044/3,037/3,045 tokens，是相同上限而非强行等长。

## 证据究竟在哪丢失

## 干预与对照补充了什么

对9例冻结关键段补回／移除、背景控制和原body重复，53条件均有效；原claim和正式预测不变。**N302最清楚**：给B补回实际bolus段，NS→S；加入背景仍NS；从A移除该段，S→NS，移除背景仍S。支持这条记录能影响本次判断，但C主臂原本含它仍NS，找到证据不保证Judge接受。

N293移除早期阳性段使C由S→NS，给B补回却仍NS，模型仍将前后状态判冲突；N394补神外段使A变S，移除该段后C却仍S；N352的“手指背景导致误判”未在对照中稳定重现。N487移除匹配平卧记录反而得到原GT的NA，说明得分与证据完整性可能背离。[全部9例控制结果与限制](interventions_001/interpretation.md)。

同期预设12次完整body重复有1次NA↔NS变化；事后困难病例18个重复有5次变化，不能把后者当总体波动率。正式三臂已事前共享相同body的答案，650×3条件＋12重复仅发送1,315个Judge请求。背景对照不是完美安慰剂，长度与位置亦有变化，每条件仅一次；诊断不是内部机制证明或人工补证系统成绩。

旧开发24条固定对照也已完成：A/B候选增至80没有统一优势；B去重排human正确7→8/12、LLM不变，样本太小；取消每note上限使LLM正确9→7/12。不能据此全局删除reranker、取消note限制或无限扩容。[开发诊断结果](development_001/analysis_001/diagnostic_metrics.json)。

## 下一步与论文定位

1. **保留C48为暂定实用baseline，A48继续作为参照。** 同预算、无新模型，避免部分路由提早丢失；human有小幅正信号，LLM基本持平。未证明稳定优越、非劣性或新算法贡献。
2. **优先验证证据组织。** 在009已经使用的开发患者上，固定候选与重排，单独比较统一的EHR标题／局部原文连接规则，检验能否保存“哪次检查—结果”“计划—执行”。有对应预算对照，不同时换查询、融合与Judge；再冻结后才用剩余开发患者确认。N430这类两路前80外缺口另记，不能期待组织解决所有召回问题。
3. **Judge是并存瓶颈。** 已有关键证据时，throughout、required、the focus、计划与实施、NS/NA边界仍造成改判；先测证据干预能解释多少，再决定是否值得专门研究支持范围。保留医学争议和原GT，不请另一个LLM代替医生重标。
4. **暂缓扩大通用planner、纯dense替代、融合公式网格及无上限扩容。** 008的28个纯空白失败已离线修复为新的开发解析条件：128可校验、16仍退回，未删失败、未生成新计划、未重评修正版planner。本轮没有证明planner在C48上仍有额外收益，也没有证明整个规划方向无效；只在基础组织较合理后仍有无法消歧的目标事件召回缺口时，才值得小规模检验其增量价值。

生成式查询扩展／改写和核验问题规划已有[Query2doc](https://aclanthology.org/2023.emnlp-main.585/)、[Query Rewriting](https://aclanthology.org/2023.emnlp-main.322/)、[RARR](https://aclanthology.org/2023.acl-long.910/)等工作。本项目可辩护的研究问题是：**在原医生命题及标签不变、没有evidence gold的个人EHR场景，证据经过候选与打包后失去了什么，改进证据与提高标签一致性何时一致、何时分离。** 009留下了受控比较和可追溯反例，尚未验证新的论文方法。可直接继续写作的[实验设置、核心表及相关工作草稿](paper_draft.md)区分了实现修正、探索观察与确认结果。
