# 007：上下文更适合用于寻找病历证据吗？

**有值得继续核查的局部召回信号，但不支持原样扩大当前版本，也不足以确立论文主线。** 来源查询确实能找回某些遗漏的手术关系、帮助零命中的 claim 获得证据；较长上下文也会挤掉关键事件。主比较没有稳定净增益，且部分“改对”来自相同输入下的 Judge 波动。下一步优先做**原 claim 约束下的证据筛选/重排**，同时完善基本召回和证据组织，不继续单纯加长查询。

本任务为执行分析与自查，等待独立复核；没有新增医生标签。007 未在同一队列直接比较“上下文放检索”与“上下文放 Judge”，因此不能通过跨 006/007 的分数证明位置优越。它验证的是：来源只参与查询、最终仍核验原 claim 时，是否产生可回查的证据和判断变化。

## 1. 实际改了什么

原作者设定使用 BGE-M3、稠密/稀疏检索及 rerank。release 保存最终 reference，但不含原检索索引、完整事实节点/向量、候选分数和精确服务版本。因此本轮新建**可追溯 BM25 词面基线**，不称为原 VeriFact 检索复现，也不把它与发布 R1 分数相减来计算方法收益。[原代码依据](https://github.com/philipchung/verifact/blob/f115d36cb65fa2073fce0a10df56bb37f4cbcd50/packages/llm_judge/src/llm_judge/reference_context.py)

使用原开发哈希顺序第 9–12 名患者 **21706、55204、65399、47874**；其 406 条有效 claim 中按固定患者/作者/标签哈希规则取 96 条，每患者/作者 12 条。LLM 为 39 S/5 NS/4 NA，human 为 27 S/9 NS/12 NA。属于诊断抽样，不能代表自然分布或全部患者；保留测试未用于选方法。

EHR 索引统一采用目标患者、目标住院的 CHARTDATE 日历日期范围，排除出院小结；原记录按空行切段，最多 640 字符，保留 note ID、日期和精确原文位置。仅改变查询：

| 检索臂 | 查询内容 |
| --- | --- |
| claim（新基线） | 原 atomic claim |
| sentence | parent 内逐字出现、与 claim 词集合重叠最高的既有来源句 |
| local | 完整 parent 加前方最多 240 个原始字符 |
| mixed（主候选） | claim 与 local 各检索一次，等权 RRF 融合，保留 claim 查询作为依据 |

四臂共用索引、BM25 参数、最多 24 片段及 9,000 字符上限；主分析按每条 claim 四臂可用量的最小值匹配证据预算。平均完整 reference 为 **7,764–7,772 字符**，实际平均输入约 **2,785–2,866 tokens**，近似可比而非严格等 token。小预算时可能截取末片，已保留原位置；这一设计的零预算缺陷见下文。

最终输入只有 **原 proposition＋实际 EHR reference**，没有来源查询、原文上下文、作者类别或 GT。Judge 均为 DeepSeek-V4-Flash、相同普通 structured、temperature=0、thinking=false、max_tokens=2048。四臂 384 次，加每患者/作者一个相同 body 的重复基线，共 **392 次**，全部有效；模型别名不是不可变权重版本。[冻结方案](../../../execution_protocol_001.md) · [输入清单](../../../preparation_003/manifest.json)

## 3. 找到的证据是否更合适

按运行中、读取新标签前保存的规则，深读改善、退化、同输入分歧和稳定对照 **18 例**：76 个完整输出、四臂实际 reference（合并重复展示后 265 个片段）；另全文读 R075/R095 的原发布 reference 各 100 条。以下是原文可核对的观察，不是模型内部机制证明或新增临床 GT。[阅读范围与逐例判断](notes_snapshot.json)

| 案例 | 证据变化与实际结果 | 能支持什么 |
| --- | --- | --- |

| [R075：体外循环后的 TEE](cases/R075_main.md) | sentence/local 增加真正的 POSTBYPASS 段并给 S；mixed 没增加该段却在同输入下改成 S。原发布 reference 53 本来就有该信息。 | 次比较有目标段落改善；主比较收益是另一回事，不能混算，也不能说原 release 全都缺证。 |

## 4. 零命中补充对照：保留而不掩盖设计边界

主分析匹配最小可用量时，**R031/R078/R083 的 claim 无词面候选，使其他有候选的臂也被清空**。这挡住了要研究的“来源救回”能力，必须披露。原结果不回写；事后按“全部预算为零的病例”这一条件另登记 3 例四臂，共 12 次，使用同一保存排名、同一 claim/Judge 和共同 9,000 字符上限。实际证据量从零增加，不能混称同有效 token 比较。

- [R031](cases/R031_sensitivity.md)：来源查询找到 stridor、BiPAP/NIV、可能再次插管的计划；NA→NS 符合 GT，不只是增加 S。
- [R078](cases/R078_sensitivity.md)：来源找到拔管、稳定、转病房/影像改善，NA→S 符合 GT。
- [R083](cases/R083_sensitivity.md)：虽找到拔管及呼吸支持资料，仍没有明确镇静撤除信息，全部 NA，不符 GT S。

因此，**零命中时的补充召回值得针对性验证**；这 3 例是事后选出的边界诊断，不能据 2 例改善宣称总体有效，也不替换上表。[追加方案与原始结果](../../../zero_budget_sensitivity_001/protocol_and_authority.json)

## 5. 是否值得作为主线，下一步做什么

当前不能判定一个环节普遍主导全部错误：18 例是有目的选例，不能估计总体病因比例。但实证上同时见到**基础词面召回漏洞、证据截取/组织缺陷，以及 Judge 的时间/状态解释和波动**。来源放在检索端让输入角色更清楚，并有局部实效；它没有自动解决所有事件对应，也没有消除原医生按独立命题标注所带来的语义边界。

推荐先做一个收紧的修订验证：**来源只补充候选，最终由原 claim 的实体、关系、显式时间/状态要求来筛选或重排证据**。保留能支持/反驳原 claim 的记录，防止长查询中的其他主题挤占证据；明确记录拒绝计划作为实施证据等判断。原 claim 没明确日期时，不把来源日期直接变成硬过滤或新增真值条件。

在此之前有两个必要控制：一是修正零预算清空和截到无关头部的问题，并加入不依赖这几个病例手工同义词的更可靠召回基线，检验 R095 等收益是否只是当前 BM25 太弱；二是未来实验预先按完整输入缓存并跨臂复用相同输入的回答，另留少量重复调用估计波动，避免把同输入改判当检索贡献。现有历史回答不选优、不改写。

**不建议现在直接上硬时间规则、再加长来源或启动微调。** event-aware retrieval 可以保留为后续候选，但要先证明其收益来自正确事件证据，而非改标签阈值、更多 token 或更弱 baseline。只有修订后在新的开发患者上重复出现证据与指标的共同改善，才值得考虑扩大并形成论文主线；当前成果是可复查的可行性与失败机制分析。
